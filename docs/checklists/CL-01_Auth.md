# Чек-лист CL-01 — Auth (Users)

| Поле | Значение |
|---|---|
| Модуль | Auth: F-01…F-05 из [Test Plan](../TEST_PLAN.md) |
| Эндпоинты | `/users/register`, `/users/login`, `/users/refresh`, `/users/logout`, `/users/logout-all` |
| Версия продукта | API v1.7.0 |
| Окружение | Local (Docker), `http://localhost:8000` |
| Исполнитель | |
| Дата прогона | |

**Легенда:**
- **Приоритет:** H — High, M — Medium, L — Low
- **Статус:** ✅ Passed · ❌ Failed · ⚠️ Blocked · ⏭ Skipped
- **❓** — требование не задокументировано явно; ожидаемый результат основан на общепринятой практике, при расхождении завести вопрос / баг
- **R-xx** — ссылка на зону риска из Test Plan

**Предусловия для всего модуля:**
1. Стенд запущен, `GET /health` → `200`, `"database": "ok"`.
2. Для функциональных проверок лимиты увеличены в `.env` (`LOGIN_RATE_LIMIT`, `REGISTER_RATE_LIMIT` = `1000/minute`). Rate limit проверяется отдельно, в [CL-03](CL-03_RateLimit.md).
3. Подготовлены два пользователя: **User A** и **User B**.
4. Для каждой проверки, где это важно, проверяется и **БД** (`docker exec -it fastapi_postgres psql -U postgres -d fastapi_db`).

## 3. Обновление токена — `POST /users/refresh` (F-03)

> Postman автоматически сохраняет cookie для домена. Для негативных проверок cookie нужно удалить или подменить через **Cookies** (под кнопкой Send) или передать вручную в заголовке `Cookie: refresh_token=<value>`.

### 3.1 Позитивные проверки

| ID | Проверка | Ожидаемый результат | Приор. | Статус | Комментарий / Баг |
|---|---|---|---|---|---|
| REF-01 | Refresh с валидным cookie | `200`, `{"access_token": "...", "token_type": "bearer"}` | H | | |
| REF-02 | Новый access token работает | `GET /items/` с новым токеном → `200`; `user_id` в payload тот же | H | | |
| REF-03 | Ротация: выдан новый refresh cookie | `Set-Cookie: refresh_token=<новое значение>` ≠ старому; атрибуты как в LOG-03 | H | | |
| REF-04 | БД после ротации | Старая запись `revoked = true`; новая запись `revoked = false`, `expires_at` ≈ now + 7 дней | H | | |
| REF-05 | Цепочка ротаций (refresh 3 раза подряд, каждый раз с новым cookie) | Каждый раз `200` | M | | |
| REF-06 | Старый access token после refresh | ❓ Остаётся валидным до истечения `exp` (stateless JWT). Зафиксировать фактическое поведение | L | | R-08 |
| REF-07 | Очистка истёкших токенов | Выставить в БД `expires_at` в прошлом у любой записи → вызвать refresh → запись удалена | L | | |

### 3.2 Негативные проверки

| ID | Проверка | Ожидаемый результат | Приор. | Статус | Комментарий / Баг |
|---|---|---|---|---|---|

| REF-09 | Пустой cookie `refresh_token=` | `401` | M | | |
| REF-10 | Случайная строка в cookie | `401`, `"Invalid or expired refresh token"` | H | | |
| REF-11 | **Повторное использование** старого refresh token после ротации | `401` | H | | R-08 |
| REF-12 | После REF-11: работает ли **новый** токен из этой же цепочки? | ❓ Повторное использование отозванного токена — признак кражи. Best practice: отозвать всю цепочку (reuse detection). Зафиксировать фактическое поведение | M | | R-08 |
| REF-13 | Refresh token, отозванный через logout | `401` | H | | |
| REF-14 | Refresh token, отозванный через logout-all | `401` | H | | |
| REF-15 | Истёкший refresh token (`expires_at` в прошлом в БД) | `401` | H | | |
| REF-16 | Access token вместо refresh в cookie | `401` | M | | |

| REF-18 | Параллельные запросы refresh с одним токеном (Postman Runner / 2 вкладки) | ❓ Успешен только один; второй → `401` (race condition) | L | | |
| REF-19 | Refresh удалённого пользователя (удалить пользователя из БД вручную) | `401` или `404`, без `500` | L | | |
