## 0. Подготовка

### 0.1 Лимиты по умолчанию (из `README.md` и `app/config.py`)

| Эндпоинт | Переменная | Лимит |
|---|---|---|
| `POST /users/register` | `REGISTER_RATE_LIMIT` | 3 / minute |
| `POST /users/login` | `LOGIN_RATE_LIMIT` | 5 / minute |
| `POST /users/refresh`, `/logout`, `/logout-all` | `DEFAULT_RATE_LIMIT` | 100 / minute |
| `GET /health` | `DEFAULT_RATE_LIMIT` | 100 / minute |
| `GET /items/`, `GET /items/all` | `ITEMS_READ_RATE_LIMIT` | 60 / minute |
| `POST /items/`, `PUT /items/{id}`, `DELETE /items/{id}` | `ITEMS_WRITE_RATE_LIMIT` | 30 / minute |
| `/docs`, `/openapi.json` (без декоратора) | `default_limits` | ❓ 100 / minute |

### 0.2 Предусловия
1. В `.env` **удалены** переопределения лимитов, сделанные для CL-01 и CL-02, то есть действуют значения по умолчанию. Исключение — раздел 6, где лимиты меняются намеренно.
2. Перед каждой проверкой счётчики сброшены одним из способов:
   - подождать 60 секунд, пока закончится окно;
   - перезапустить API: `docker-compose restart api`. Счётчики хранятся в памяти процесса — это также проверяется в RL-41.
3. Подготовлен залогиненный пользователь (`{{token}}`) и refresh-cookie.
4. Перед проверками login/register токен лучше получить заранее, чтобы логин в подготовке не расходовал лимит.

### 0.3 Инструменты для серии запросов

**Postman Collection Runner** — запрос в отдельной папке, `Iterations = N + 1`, `Delay = 0`. В Tests можно логировать статус: `console.log(pm.info.iteration, pm.response.code)`.

**curl-цикл** (удобнее для подсчёта):

```bash
for i in $(seq 1 6); do
  printf "%s: " "$i"
  curl -s -o /dev/null -w "%{http_code}\n" -X POST http://localhost:8000/users/login \
    -H "Content-Type: application/json" \
    -d '{"email":"rl@test.com","password":"wrong"}'
done
```

Вывод заголовков и тела последнего ответа: `curl -i ...`.

## 5. Какие запросы учитываются

> Проверки этого раздела выясняют, расходуется ли лимит запросами, которые отклоняются **до** выполнения эндпоинта (валидация тела, авторизация). Для каждой: отправить 10 «плохих» запросов, затем 1 корректный.

| ID | Проверка | Ожидаемый результат | Приор. | Статус | Комментарий / Баг |
|---|---|---|---|---|---|
| RL-33 | Неудачные логины (`401` неверный пароль) учитываются | 5 × `401` → 6-й `429` | H | | |
| RL-34 | Логины с невалидным телом (`422`) учитываются | ❓ 10 × `422` (например, `email: "abc"`) → ожидание: уже после 5-го приходит `429`. Если все 10 вернули `422`, лимит обходится невалидными запросами | M | | |
| RL-35 | Регистрация дубликата (`400`) учитывается | 3 × `400` → 4-й `429` | M | | |
| RL-36 | Запросы к items без токена (`401` / `403`) | ❓ Зафиксировать: учитываются ли неавторизованные запросы. Отправить 61 запрос `GET /items/` без токена | M | | |
| RL-37 | Запросы с невалидным токеном | ❓ Аналогично RL-36 с `Authorization: Bearer invalid` | L | | |
| RL-38 | Запросы, отклонённые с `429`, не создают побочных эффектов | После RL-09 и RL-02 в БД нет лишних записей; в `refresh_tokens` нет лишних токенов после RL-01 с верным паролем | H | | |
| RL-39 | Запись `429` в логи | ❓ Зафиксировать, логируются ли превышения лимита (в `logs` и в `docker-compose logs api`). Для анализа атак это полезно | L | | R-12 |
